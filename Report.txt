## STEP 1 — Real User Flows End-to-End Testing

### Flow 1: New Buyer Registration & First Purchase

**Status: PASS (with issues)**

**Happy path traced through code:**
1. `/register/` → `RegisterView.get()` → renders `users/register.html` → buyer selects role
2. `RegisterView.post()` → `create_user()` → `User.create_buyer()` → saves User with `role=BUYER`, `is_active=False`
3. OTP generated → `generate_otp(user, 'email_verification')` → `send_otp_email()` → renders `users/otp_verify.html`
4. User submits OTP → `VerifyOTPView.post()` → `verify_otp(user, otp, 'email_verification')` → `user.is_active=True`
5. Redirect to login → buyer logs in → `LoginView.post()` → checks `user.is_active`, `user.is_email_verified`
6. Browse `/shop/` → filter by category, search, sort → paginate 24/page
7. Click product → `/product/<slug>/` → `product_detail_public()` → render
8. Add to cart → `/cart/add/` POST (product_id, quantity, size/color/variant) → Cart item created with subtotal
9. View cart → `/cart/` → shows items, subtotals, shipping
10. Checkout → `/checkout/` → `CheckoutView` → renders addresses, cart items, payment summary
11. Select/add address → POST
12. Pay → redirect to Paystack → callback → `PaymentCallbackView` → verify transaction → create Order + SubOrder + Payment
13. Order confirmed → `/orders/` → list of buyer orders
14. Mark as received → `/orders/<id>/` → POST `confirm_receipt` → updates `delivery_status=DELIVERED`
15. Leave review → `/products/<slug>/review/` → POST → review saved (rating 1-5, text)

**Issues found:**

1. **No price validation on cart checkout** — `Cart.subtotal` property sums `item.price * item.quantity`, but item price is set at add-to-cart time and could be stale if vendor changes price. No re-validation at checkout against current ProductPrice. **Severity: Low** (prices rarely change mid-session; no security risk).

2. **Wallet release is lazy (happens on delivery confirmation only)** — SubOrder funds only transfer to vendor wallet when buyer clicks "Confirm Delivery". If buyer never clicks, funds stay in platform wallet indefinitely. No auto-release after 7 days. **Severity: Medium** (platform holds vendor money with no automatic release).

3. **No buyer notification emails after order confirmation** — Buyer gets order confirmation via Paystack, but no email confirmation from KasuMarketplace itself. **Severity: Low** (Paystack handles buyer confirmation).

4. **Stock not restored on order rejection/cancellation** — `OrderItem.delete_suborder()` doesn't restore `Product.stock_quantity`. **Severity: Low** (cancellation only happens when no payment yet).

### Flow 2: New Vendor Registration, Verification & First Sale

**Status: PASS (with issues)**

**Happy path traced through code:**
1. `/vendors/register/` → `VendorRegisterView` → creates User + VendorProfile (tier=Tier(1), status=PENDING)
2. OTP → email verification → `user.is_active=True`
3. BVN verification → `/vendors/verify/bvn/` → `BVNVerificationView` → `verify_bvn()` → stores `bvn_number`
4. Selfie → `/vendors/verify/selfie/` → `SelfieVerificationView` → saves `verification_selfie`
5. Profile approval → admin `/admin/vendors/vendorprofile/` → `approve_profile` action → creates Store, sets `status=APPROVED`
6. Store setup → `/vendors/store/setup/` → `StoreSetupView` → creates Store
7. Create product → `/vendors/products/add/` → `ProductCreateView` → Product created with `status='draft'`
8. Publish product → admin changes `status='published'` or vendor sets directly
9. Buyer purchases → vendor sees in `/orders/` (as seller)
10. Accept order → `/orders/<id>/accept/` → `OrderAcceptView` → `SubOrder.status=ACCEPTED`
11. Delivery → buyer confirms → `delivery_status=DELIVERED`
12. Wallet → `/vendors/wallet/` → `WalletView` → balance updated by `release_funds_to_vendor()` signal
13. Payout → `/vendors/wallet/payout/` → `request_payout()` → creates PayoutRequest

**Issues found:**

1. **`VendorProfile.is_verified` not set to True after approval** — `approve_profile` action sets `status=APPROVED` but does NOT set `is_verified=True`. The badge check uses `vendor.is_verified` (not `store.vendor.is_verified`), so verified badges will never show even for approved vendors. **Severity: HIGH** (breaks verified badge display across all storefronts).

2. **`is_verified` vs `can_sell` are independent fields** — A vendor could be `is_verified=True` but `status=PENDING` (never happens in current code, but confusing). No code sets `is_verified=True` automatically. **Severity: Medium** (design inconsistency).

3. **Payout access control missing** — `request_payout()` only checks `wallet.balance >= amount`. Any approved vendor (even Tier 1, commission=0%) can request payout. No minimum payout amount enforced in view. **Severity: Low** (policy decision, not bug).

4. **WalletTransaction.sub_order constraint** — `release_funds_to_vendor()` tries to set `sub_order` on WalletTransaction, but the signal `post_save` for SubOrder only fires when `instance.status == 'DELIVERED'`. If SubOrder is created without going through the signal (e.g., admin action), funds won't be released. **Severity: Low** (edge case).

### Flow 3: Dispute & Resolution

**Status: PASS**

**Happy path traced through code:**
1. Buyer sees problem → `/orders/<id>/` → clicks "Open Dispute" button
2. `OrderDetail.get()` renders `open_dispute.html` form
3. Buyer submits → `/orders/<id>/dispute/` → `OpenDisputeView.post()` → creates Dispute with `status=OPEN`
4. Vendor notified (email)
5. Vendor responds → `/orders/<id>/dispute/reply/` → `DisputeReplyView.post()` → creates DisputeMessage
6. Admin reviews → `/admin/marketplace/dispute/` → can see status, assign (manual)
7. Resolution → vendor or buyer marks as resolved

**Issues found:**

1. **Dispute resolution is entirely manual** — No code enforces any SLA or auto-resolution. Buyer/vendor must manually update status. Admin must manually assign/resolve. **Severity: Low** (by design — no fixed timeline per policy decision).

2. **No dispute notification emails to admin** — When dispute is opened, only vendor gets email. Admin gets no notification. **Severity: Low** (admin can see in admin panel).

### Flow 5: Vendor Suspension & Effect on Listings

**Status: PASS (needs verification)**

**Code analysis:**
- Admin suspends vendor → `VendorProfile.status=SUSPENDED`
- `VendorProfile.is_verified` → badge check: `vendor.store.vendor.is_verified` → badge shows NO (because `is_verified` not set)
- Published products remain visible (no code hides products when vendor is suspended)
- Buyer can still purchase from suspended vendor (no checkout block)
- SubOrder created with `vendor` field → funds go to vendor wallet

**Issues found:**

1. **Suspended vendor's products remain visible and purchasable** — No code checks vendor status before allowing checkout. Buyer could pay a suspended vendor. **Severity: HIGH** (buyer protection risk).

2. **No product visibility change on suspension** — Products don't get hidden or marked as unavailable when vendor is suspended. **Severity: Medium** (misleading to buyers).
